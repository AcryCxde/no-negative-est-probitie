# bot_2: тренировочные и рейтинговые бои

Python 3.12.9. Проект находится в `bot_2/battleship_hack/`; все команды выполняются из этой папки.

Документация бота: [общее описание и устройство](docs/README.md), [история развития и неудачные подходы](docs/CHANGELOG.md). Подробные результаты серий — в [журнале экспериментов](experiments/bot2.md).

```bash
uv sync --python 3.12.9
uv run battleship-hack smoke
```

Создайте `.env` по образцу `.env.example` в этой папке либо в родительской `bot_2/`:

```dotenv
BOT_TOKEN=<локальный токен бота>
BOT_PLATFORM_ID=<необязательный UUID бота из кабинета/адреса его страницы>
```

Необязательное поле можно оставить пустым. Токен читается из файла, не передаётся в аргументах и не пишется в журналы. `.env`, журналы, БД и окружение исключены из Git.

## Один тренировочный бой

```bash
uv run battleship-hack run --bot bot2 --config configs/bot2.toml --opponent EASY --matches 1
```

Клиент первой командой запрашивает `TRAINING`, играет назначенные матчи, после одного `MATCH_FINISHED` закрывает соединение и импортирует журнал в DuckDB. Общий лимит ожидания/работы — 360 секунд; можно изменить через `--max-seconds`. `--seed` задаёт воспроизводимую случайность, `--experiment` — имя эксперимента. Стратегии выбираются через `--strategy`: `baseline` (случайный поиск), `density` (карта допустимых положений оставшихся кораблей), `fleet-mc` (выборка согласованных целых флотов в поиске, карта положений при добивании), `hard-edge` (экспериментальная модель расстановки HARD). `baseline` и `fleet-mc` сохранены для сравнения.

**TRAINING меняет Elo (K=10)**, хотя не расходует первые 10 рейтинговых матчей. Настоящего режима без изменения рейтинга в спецификации нет. Бонусы и ставки эта версия не использует.

## Рейтинговые бои

```bash
uv run battleship-hack run --mode RANKING --matches 10 --max-seconds 3600 --experiment ranking-fleet-mc
```

С основной конфигурацией в RANKING используется `fleet-mc`. По явному выбору можно проверить `hard-quadrants` против командных соперников; эта модель подтверждена на HARD и возвращается к fleet-mc при противоречащих наблюдениях. `hard-edge` отдельно доступна только для TRAINING/HARD. После указанного числа завершённых боёв клиент отключается; общий лимит времени задаёт `--max-seconds`.

Для «Спидрана» клиент переключается на `fleet-mc-speedrun-v2`: поиск по расстановке HARD и добивание целыми флотами как в `fleet-mc-hunger-v2`. `PLACE` не отправляется, бонусы не тратятся. Откат поиска — `--strategy fleet-mc-speedrun`.

```bash
uv run battleship-hack run --mode RANKING --strategy fleet-mc-speedrun-v2 --matches 5 --max-seconds 3600 --experiment speedrun-v2-ranking
```

Проверка Спидрана: 25 живых боёв, 20 побед; v2 — 15/20, после исправления повторных выстрелов — 5/5. На 20 одинаковых раскрытых полях × 3 seed: hunger-v2 62,47 / speedrun 45,20 / speedrun-v2 44,20 выстрела. Клиент ждёт результат отправленного выстрела при задержке, чтобы новый запрос хода после таймаута не создавал дубль. [Результаты и ограничения сравнения](experiments/speedrun-review.md).

Для «Голодных игр» добавлена экспериментальная `fleet-mc-hunger-v2`: расстановка по карте поисковых выстрелов команды из `fleet-mc-hunger-heat`, добивание по согласованным целым флотам с оценкой двух следующих выстрелов (одного, если остался последний), SHIELD только вне нашего добивания и при высокой точности соперника. Базовая `fleet-mc-hunger` доступна для сравнения. Лимит выстрелов приходит от сервера в `MATCH_STARTED.rules.shotLimitPerPlayer`; `--matches` задаёт число партий, а `--experiment` — метку журнала.

```bash
uv run battleship-hack run --mode RANKING --strategy fleet-mc-hunger-v2 --matches 10 --max-seconds 3600 --experiment hunger-v2-ranking-20
# Локальное сравнение только стрельбы, 160 досок каждого типа, 20 выстрелов:
uv run python scripts/sim_hunger.py 160 20 hunger hunger-v2
```

Разбор исходной стратегии и ограничения офлайн-сравнения: [hunger-ranking-20-review.md](experiments/hunger-ranking-20-review.md).

```bash
uv run battleship-hack run --config configs/bot2-ranking.toml --experiment hard-quadrants-ranking-5
```

Эта отдельная конфигурация задаёт RANKING, hard-quadrants, пять боёв и лимит 1800 секунд. При доступной HTTP-статистике своей команды клиент прекращает сессию, если ему назначен соперник с тем же teamName.

**Стартовая гонка платформы:** подключение по умолчанию находится в RANKING, а CHANGE_MODE действует со следующего матча. Если рейтинговый соперник назначен при запуске тренировки, клиент расставляет флот и играет `fleet-mc`, затем продолжает в запрошенном режиме. Такой бой также учитывается в `--matches`. Новый процесс восстанавливает существующий MATCH_SNAPSHOT универсальной стратегией; при неизвестном сопернике вид партии не выдумывается. Флот отправляется только при отсутствии принятой расстановки и открытом окне размещения, кроме SPEEDRUN.

## Что уже работает

- `asyncio` + JSON/WebSocket, Bearer-заголовок, ping, ограничение частоты и размера исходящих сообщений.
- Правила из каждого `MATCH_STARTED`; случайная допустимая расстановка с проверкой и коротким бюджетом времени.
- Переключаемые baseline/density/fleet-mc/hard-edge; пустые диагонали и ореолы при известном запрете касания, добивание по допустимым положениям; `DEFENDED` допускает повторный выстрел.
- Действие только по `TURN_REQUESTED`, одна команда за запрос. Базовая поддержка модификаторов, включая отсутствие `PLACE` в `SPEEDRUN` и отсутствие `SUNK` в `SCHRODINGER_SHIP`.
- Ограниченное переподключение и восстановление принятых выстрелов из `MATCH_SNAPSHOT` внутри текущего процесса. Без слепого повтора незавершённой команды.
- Остановка при неверном токене, блокировке, замене соединения и перевыпуске токена. Локальный lock предотвращает второй процесс из этой рабочей папки.
- Два smoke-теста без внешнего сервера и секретов: обмен с локальным WebSocket-сервером, включая reconnect; журнал, DuckDB и отчёт.

## Наблюдаемость

`data/bot2/logs/<run_id>.jsonl` хранит входящие/исходящие сообщения, решения, ошибки, подключения, исходы и измеренное время от начала обработки запроса до отправки команды. Каждая запись сбрасывается в файл. Это не измерение полной задержки от сервера до сервера. Локальный `battle_id` отличается от платформенного `matchId`.

`data/bot2/versions/<run_id>/` хранит снимок исходников и конфигураций, хеш, Git commit и признак незакоммиченных изменений. `.env` в снимок не попадает.

При наличии `BOT_PLATFORM_ID` клиент получает публичную HTTP-статистику до/после запуска и журнал после отключения. Сопоставление боя с `matchId` — по времени, типу и идентификатору соперника и исходу, только при единственном кандидате; это эвристика. При неоднозначности и без UUID платформа/рейтинг остаются `NULL`, локальные результаты доступны. HTTP-расчёт рейтинга может появиться с задержкой. Ошибка HTTP не мешает самому бою.

```bash
uv run battleship-hack ingest
uv run battleship-hack report
# Импорт экспортированных JSONL в отдельную сводную БД
uv run battleship-hack ingest --logs /path/to/exported/logs --db data/team-summary.duckdb
```

DuckDB содержит `events` и представления `runs`, `battles`, `experiments`. Повторный импорт не дублирует `event_id`; незавершённая последняя строка JSONL ждёт следующего импорта. БД не используется во время боя, импорт выполняется одним процессом после закрытия сокета. Для анализа одновременно с импортом используйте копию БД. Отчёт показывает исходы, долю побед среди завершённых боёв, доступные изменения рейтинга, mean/p95 времени решений и диагностические события.

Пример SQL для анализа через Python/DuckDB:

```sql
SELECT strategy, status, outcome, end_reason, rating_change FROM battles;
SELECT type, count(*) FROM events GROUP BY type ORDER BY count(*) DESC;
```

Гипотезы и выводы записывайте в `experiments/bot2.md`. Первая цель — проверить подключение, расстановку, обмен ходами и сохранение результатов; качество алгоритма пока не оцениваем.

Спецификация: [протокол](../../docs/platform/guide.md), [сообщения](../../docs/platform/messages.md), [ошибки](../../docs/platform/values.md), [HTTP](../../docs/platform/http-api.md). Исследование: [стратегии](../../docs/research/research.md).


## Проверка улучшенной стратегии против MEDIUM

```bash
uv run battleship-hack run --strategy fleet-mc --opponent MEDIUM --matches 5 --max-seconds 900 --experiment fleet-mc-medium-v1
```

Остающийся флот обновляется по SUNK. Поиск учитывает промахи, пустые диагонали, ореолы потопленных кораблей и совместимость всех оставшихся кораблей. Добивание ограничивается допустимыми прямыми положениями, а не случайным обходом всех соседей. Выборка ограничена 80 мс (или 12% серверного дедлайна) и 1000 принятыми флотами; при недостаточной выборке применяется density. Это приближённая карта: последовательный генератор смещён, точного равномерного/байесовского распределения не обещаем. Число сэмплов пишется в обоснование DECISION. Seed фиксирует случайность, но ограничение по времени делает точное повторение MC-запуска зависимым от скорости машины.


Текущая конфигурация по умолчанию: `fleet-mc`, `MEDIUM`, **1 бой**. В первой реальной серии fleet-mc выиграл 5/5 тренировок MEDIUM без ошибок, среднее 59,4 выстрела, p95 выбора/отправки хода 50,458 мс. Это короткая серия, не доказательство стабильного 100% винрейта или статистически значимого превосходства baseline. Простой откат выбора стратегии: `--strategy baseline`.

```bash
# Один бой текущей стратегии
uv run battleship-hack run --opponent MEDIUM --matches 1 --experiment fleet-mc-medium
# Контрольная стратегия
uv run battleship-hack run --strategy baseline --opponent MEDIUM --matches 1 --experiment baseline-medium
```

## Стратегия для HARD

`hard-edge` проверяет гипотезу из [разбора HARD](experiments/hard-analysis.md): многопалубные корабли целиком на периметре, катера внутри. В поиске MC строит согласованные флоты из таких положений; при добивании используется та же модель. Когда остаётся один катер, выбор среди допустимых внутренних клеток делается без шума MC. Наша расстановка остаётся общей, чтобы отдельно оценить изменение стрельбы.

```bash
uv run battleship-hack run --strategy hard-edge --opponent HARD --matches 1 --experiment hard-edge-v1
# Контроль той же сложности
uv run battleship-hack run --strategy fleet-mc --opponent HARD --matches 1 --experiment fleet-mc-hard-control
```

CLI требует `--opponent HARD` для `hard-edge`. Это наблюдаемый шаблон соперника, а не правило платформы: при внутреннем HIT, катере на краю, потопленном многопалубном корабле вне периметра, отсутствии согласованных положений или недостаточной выборке бот до конца партии переключается на fleet-mc. При модификаторе или другом правиле касания используется fleet-mc с начала партии. Модель и причина переключения пишутся в `DECISION.reason`; при reconnect противоречия восстанавливаются из истории результатов. Временный fallback из-за недостаточной выборки может не повториться после reconnect, но наблюдаемое противоречие повторится.

Default остаётся `fleet-mc` / MEDIUM; для HARD стратегию задавайте явно. Рост процента побед нужно подтвердить серией боёв.

## Поиск катеров по четвертям

`hard-quadrants` сохраняет атаку крупных кораблей из `hard-edge`. Для обычного поля 10×10 с четырьмя катерами она проверяет дополнительную гипотезу: ровно один катер в каждой четверти. Граница проходит между строками 4/5 и столбцами 4/5 (координаты с нуля). Во всех 13 полностью раскрытых полях HARD из 29 прошлых матчей это выполнялось; среди всех 88 найденных катеров повторов четверти в одном матче не было. Поля поражений раскрыты не полностью.

После уничтожения многопалубных кораблей стратегия точно считает совместимые расстановки катеров: по одному в каждой четверти, где катер ещё не потоплен, с учётом всех известных пустых клеток и запрета касания между четвертями. Выбирается клетка с максимальной долей занятости, ничьи разрешаются по seed. Для последнего катера поиск ограничен оставшейся четвертью. Подсчёт ограничен 80 мс или 12% дедлайна хода; это точная карта в рамках гипотезы о четвертях, а не знание серверного генератора.

```bash
uv run battleship-hack smoke
uv run battleship-hack run --strategy hard-quadrants --opponent HARD --matches 1 --experiment hard-quadrants-v1
# Контроль предыдущей стратегии
uv run battleship-hack run --strategy hard-edge --opponent HARD --matches 1 --experiment hard-edge-control
```

Два обнаруженных катера в одной четверти, несогласованное число катеров/четвертей, отсутствие согласованных расстановок или исчерпание времени отключают гипотезу четвертей до конца партии и возвращают `hard-edge`. Другие размеры поля/флот используют `hard-edge`; его собственный fallback на fleet-mc сохраняется. Четверти потопленных катеров восстанавливаются при replay/snapshot. В `DECISION.reason` записываются `exact_layouts`, `estimated_hit`, `sectors_left` и причины fallback. В TRAINING CLI требует HARD; явный эксперимент в RANKING также разрешён. Наша расстановка сохранена.
