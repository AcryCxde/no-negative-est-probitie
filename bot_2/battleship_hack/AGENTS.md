# Морской бой: инструкции для Codex и Cursor

## Рабочая область

Этот проект расположен в `bot_2/battleship_hack/` общего репозитория команды `/Users/cawakowa/dev/no-negative-est-probitie`. Работай только внутри `bot_2/`: код, зависимости, конфигурации, журналы, БД и эксперименты этого участника находятся здесь. Все команды ниже выполняются из `bot_2/battleship_hack/`.

Текущий участник отвечает за `bot2`. Папки `bot_1/` и `bot_3/` принадлежат другим участникам; не изменяй их и файлы корня общего репозитория без явного указания пользователя. Описание трёх ботов ниже задаёт командные договорённости, а не требует реализовать или запускать соседних ботов в этом проекте. CLI, smoke-проверки и отчёты этого проекта по умолчанию относятся только к `bot2`; примеры для других ботов описывают аналогичный интерфейс в их собственных проектах.

## Цель и приоритеты

Это хакатонный проект, а не production-сервис. Цель — получить максимальный рейтинг и победить за счёт многократных боевых итераций над алгоритмами и стратегиями трёх ботов.

Приоритеты: корректность по правилам и API → быстрый запуск в бой → измеримый рост рейтинга → скорость следующей итерации. Предпочитай простое рабочее решение. Не добавляй инфраструктуру, абстракции, зависимости и проверки без практической пользы для ближайших боёв.

## Стек и спецификация

- Python **3.12.9**, пакет в `src/battleship_hack`, управление окружением и зависимостями через `uv`.
- Основные среды разработки — Codex и Cursor. Этот файл задаёт общие инструкции для работы с репозиторием.
- Серверный транспорт — WebSocket, обмен сообщениями-событиями разных типов в формате **JSON**. Для сетевого клиента используй `asyncio`; структуру JSON и типы событий бери из спецификации.
- Спецификация уже доступна: [правила и протокол](../../docs/platform/guide.md), [сообщения](../../docs/platform/messages.md), [значения и ошибки](../../docs/platform/values.md), [HTTP API](../../docs/platform/http-api.md). Исследование стратегий — [research.md](../../docs/research/research.md). Перед изменениями читай соответствующие разделы. Правила конкретной партии бери из `MATCH_STARTED`/`MATCH_SNAPSHOT`.
- Не выдумывай типы событий, поля сообщений, порядок ходов, ограничения размещения кораблей, таймауты и формулу рейтинга. До получения спецификации можно готовить каркас и изолированные алгоритмы; неподтверждённые предположения явно помечай.
- При расхождениях правила и API из спецификации определяют поведение бота, этот файл — подход к разработке.

## Команда, три бота и стратегии

- Команда состоит из трёх человек. Каждый участник отвечает за своего бота: его стратегии, эксперименты и результаты. Поддерживай три независимо запускаемых экземпляра: `bot1`, `bot2`, `bot3`. У каждого свои учётные данные, конфигурация, состояние партии, журнал и локальные данные.
- Переключение стратегий применяется к одному выбранному боту. У каждого бота свой набор стратегий и baseline; смена стратегии или параметров одного бота не меняет настройки остальных. Проверяй, что выбранная стратегия доступна этому боту.
- Изолируй код и конфигурации стратегий по ботам, чтобы участники могли работать независимо. Изменения общего клиента, модели состояния и формата журналов сохраняют совместимость всех трёх ботов; согласовывай изменения общих интерфейсов с командой.
- Общий клиент протокола и модель состояния переиспользуй. Алгоритмы размещения кораблей и выбора ходов держи отдельно от сетевого кода, чтобы менять их быстро.
- Стратегия получает актуальное состояние и возвращает допустимое решение. Не создавай универсальный фреймворк плагинов: простой интерфейс и реестр стратегий достаточны.
- Сохраняй текущую лучшую стратегию каждого бота как его baseline. Экспериментальные изменения не должны мешать быстро вернуть её и запустить снова.
- Для случайных решений поддерживай задаваемый seed и сохраняй его в результатах. Не смешивай состояние разных ботов или партий.

## Цикл разработки

1. Сформулируй конкретную гипотезу: какое поведение меняется и почему это должно улучшить результат.
2. Внеси минимальное изменение. Если возможно, оставь его за параметром или отдельным именем стратегии.
3. Выполни короткую smoke-проверку, затем запускай бои в рамках разрешённого пользователем доступа к серверу.
4. Сравни эксперимент с baseline своего бота на серии боёв. По возможности чередуй стратегии на этом же боте и сохраняй сопоставимые условия. Командные результаты сравнивай с учётом различий рейтинга и подбора соперников; не приписывай эти различия только качеству алгоритма.
5. Зафиксируй конфигурацию, число боёв, победы/поражения/ничьи, изменение рейтинга, ошибки и вывод. Отделяй наблюдения от гипотез; не объявляй стратегию лучшей по одному удачному бою.
6. Оставь выигрышное изменение либо быстро откати эксперимент. Повтори цикл.

Не трать время на долгие исследования и большие рефакторинги, если можно проверить гипотезу в бою. Если сервер недоступен, продолжай полезную локальную работу и явно сообщи, что боевая проверка не состоялась.

## Запуск и команды

Рабочие команды окружения и проверки синтаксиса:

```bash
uv sync --python 3.12.9
uv run python --version
uv run python -m compileall -q src
```

Реализованы команды только текущего бота `bot2`:

```bash
uv run battleship-hack smoke
uv run battleship-hack run --bot bot2 --strategy baseline --config configs/bot2.toml --opponent EASY --matches 1
uv run battleship-hack ingest --bot bot2 --logs data/bot2/logs --db data/bot2/analytics.duckdb
uv run battleship-hack report --bot bot2 --db data/bot2/analytics.duckdb
```

Токен читается из `.env` проекта или родительской `bot_2/.env`: `BOT_TOKEN`. `BOT_PLATFORM_ID` — необязательный UUID для HTTP-аналитики. CLI этой версии поддерживает только TRAINING и завершает запуск после заданного числа партий; бонусы и ставки не применяет. TRAINING тоже меняет Elo. При подключении сервер по умолчанию назначает RANKING; переключение режима не отменяет уже начатую партию. Учитывай эту гонку перед сетевым запуском; клиент останавливается при сопернике команды или неизвестном снимке существующей партии.

Каждого бота должно быть удобно запускать в отдельном терминале, останавливать и перезапускать после изменения. URL сервера и параметры задавай конфигурацией, секреты — переменными окружения. При добавлении параметров документируй их в `--help` и README. Не показывай несуществующие команды как проверенные.

## Минимальные проверки

- Основная проверка качества стратегии — реальные бои. Полное покрытие, большие наборы unit-тестов, CI и сложные моки сервера не нужны без отдельной задачи.
- Достаточно одной-двух быстрых smoke-проверок: загрузка конфигураций и доступных каждому боту стратегий; обработка минимальной последовательности известных JSON-событий с выдачей допустимого хода, записью журнала, повторным импортом без дублей и получением сводки из временной БД. До спецификации проверяй только подтверждённые части.
- Smoke выполняется локально, за секунды, без сетевых запросов и секретов; при ошибке завершает процесс ненулевым кодом.
- Добавляй небольшой регрессионный тест только если он дёшево предотвращает повторение конкретного сбоя, который мешал боевым итерациям.

## WebSocket и устойчивость в бою

- Сосредоточь защиту на сбоях, которые теряют партии: неверные сообщения, рассинхронизация состояния, зависание и разрыв соединения. Соблюдай порядок и сроки действий из спецификации.
- Логируй неизвестные типы событий и обрабатывай их согласно протоколу. Ошибки стратегии и клиента должны быть заметны, а не скрываться широким `except`.
- Не отправляй повторно ход после reconnect вслепую. Восстановление партии, подтверждения, дедупликацию и повторные отправки реализуй только в соответствии с API.
- Не блокируй цикл `asyncio` долгими вычислениями. Если поиск дорогой, ограничивай его бюджетом времени с учётом серверного дедлайна.
- Завершение по Ctrl+C должно закрывать соединение и сохранять доступные результаты.

## Наблюдаемость и артефакты

Наблюдаемость и логируемость — обязательная часть первой рабочей версии. Каждый бой должен оставлять данные, по которым можно восстановить ход событий, объяснить ошибку и сравнить стратегии.

- Для каждого запуска сохраняй уникальный `run_id`, `bot_id`, `experiment_id`, стратегию, параметры, seed, время UTC и версию кода; при незакоммиченных изменениях отмечай это и сохраняй снимок изменений без секретов.
- Для каждого боя сохраняй доступные по API идентификатор партии, результат, рейтинг до/после и его изменение, число ходов, время принятия решений и ошибки. Незавершённые и прерванные партии отмечай отдельно. Недоступные данные храни как `NULL`, не подменяй нулём и не придумывай.
- Записывай входящие и исходящие JSON-события, решения стратегии и их краткое обоснование, соединения/разрывы, ошибки разбора и исключения. Сохраняй исходную структуру payload после удаления секретов; неизвестные поля не отбрасывай. Для некорректного JSON сохраняй очищенный исходный текст и причину ошибки.
- У каждой записи должны быть версия формата журнала, уникальный `event_id`, время UTC, последовательный номер внутри запуска, `bot_id`, `run_id`, доступный идентификатор партии, направление/категория, тип события и payload. Это поля локального журнала, а не требования к серверному API.
- Основной журнал — append-only JSONL в `data/<bot_id>/logs/<run_id>.jsonl`; терминал показывает короткую текущую сводку. Регулярно сбрасывай буфер и сбрасывай его при завершении боя/процесса. Не обещай сохранность ещё не записанного буфера при аварийном завершении.
- Запись журналов не должна заметно задерживать ход. При использовании очереди ограничивай её размер; ошибки записи и переполнение показывай явно. Не теряй события молча и не скрывай сбой наблюдаемости.

### Простая БД и анализ

- По умолчанию используй **DuckDB** как локальную файловую БД и SQL-движок анализа. JSONL — первичный журнал, БД — восстанавливаемое представление для запросов. Не вводи отдельный сервер БД, ORM и сервис телеметрии без конкретной необходимости.
- У каждого участника отдельная БД `data/<bot_id>/analytics.duckdb`. Импорт выполняет один процесс-писатель на файл БД; боты пишут только свои JSONL. Не организуй совместную запись нескольких процессов в один файл DuckDB. Для анализа во время импорта используй согласованный снимок или дождись завершения импорта.
- Минимальные сущности: `runs`, `events`, `battles`, `experiments`. Часто используемые поля храни в типизированных колонках, переменные параметры, метрики и payload — в JSON. Новые поля событий не должны требовать изменения схемы на каждом эксперименте. Для изменений стабильных колонок достаточно простых версионированных SQL-миграций.
- Импорт должен быть повторяемым без дублей по локальным идентификаторам. Обрабатывай только завершённые строки активного JSONL; неполную последнюю строку дочитывай при следующем импорте. Повреждённые записи показывай в диагностике, сохраняя исходный журнал.
- Обеспечь простые SQL-запросы и CLI-сводки: текущий и исторический рейтинг, число завершённых/прерванных боёв, доля побед с явным знаменателем, изменение рейтинга, сравнение стратегий и параметров, среднее и p95 времени решения, ошибки и разрывы соединения.
- Для командного анализа поддержи импорт экспортированных журналов участников в отдельную сводную БД с сохранением `bot_id`, `run_id` и `experiment_id`. Общая БД не нужна для запуска ботов.
- Веди краткий журнал гипотез и выводов в `experiments/<bot_id>.md`: `experiment_id`, гипотеза, версия/конфигурация, размер выборки, результат, следующий шаг. Численные результаты получай из БД; Markdown хранит человеческую интерпретацию и ссылки на запуск.
- Токены и другие секреты удаляй до записи в любой журнал, БД, снимок конфигурации или экспорт. Локальные секреты, БД и объёмные журналы исключай через `.gitignore`; пример конфигурации храни без секретов.

## Как работать агенту

- Сначала прочитай спецификацию, если она уже есть, и затронутый код. Затем действуй самостоятельно в рамках задачи: не останавливайся ради согласования обычных обратимых решений.
- Делай небольшие изменения, которые легко проверить в бою и откатить. Сохраняй пользовательские изменения; не очищай рабочее дерево и результаты экспериментов.
- Не улучшай посторонние части проекта и не вводи production-практики ради самих практик.
- По завершении кратко сообщи: что изменено, точные команды запуска/проверки, что действительно проверено и какой боевой эксперимент выполнить следующим. Если бои проведены, приведи измеренные результаты.
